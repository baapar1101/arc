# برنامه استاندارد افزونه «ورود لایو اطلاعات از سپیدار»

## هدف و مرز ایمنی

افزونه یک اتصال **فقط‌خواندنی** به SQL Server سپیدار برقرار می‌کند و نسخه‌ای قابل‌ردیابی از داده‌ها را در PostgreSQL حسابیکس نگه می‌دارد. هیچ `INSERT`، `UPDATE` یا `DELETE` روی سپیدار انجام نمی‌شود. اطلاعات اتصال رمزنگاری می‌شوند و رمز عبور هرگز در پاسخ API یا Git ثبت نمی‌شود.

## معماری

1. تنظیم اتصال برای هر کسب‌وکار: سرور، پورت، دیتابیس، کاربر، رمز، دوره اجرا، batch size و فیلتر schema/table.
2. کشف ساختار از `INFORMATION_SCHEMA`: جدول‌ها، ستون‌ها و کلید اصلی بدون اعتماد به نام ورودی کاربر.
3. Snapshot خام و کامل: هر رکورد سپیدار با کلید پایدار، payload JSON، hash محتوا و زمان مشاهده در حسابیکس ذخیره می‌شود.
4. همگام‌سازی idempotent: اجرای مجدد رکورد تکراری نمی‌سازد؛ رکورد تغییرکرده به‌روزرسانی می‌شود.
5. اجرای لایو: worker داخلی فقط تنظیمات فعال و موعدرسیده را اجرا می‌کند و به‌کمک lock پایگاه‌داده از اجرای همزمان جلوگیری می‌شود.
6. مشاهده‌پذیری: تاریخچه اجرا، تعداد جدول/رکورد، مدت، خطا و آخرین موفقیت ثبت می‌شود.

## فازهای انتقال

- فاز ۱ (این پیاده‌سازی): mirror کامل و امن تمام جدول‌های انتخاب‌شده؛ مناسب حفظ همه اطلاعات و تحلیل/نگاشت بعدی.
- فاز ۲: نگاشت موجودیت‌های اصلی به مدل بومی حسابیکس (اشخاص، کالا، انبار، فاکتور، دریافت/پرداخت، سند حسابداری) با جدول mapping و سیاست تعارض قابل انتخاب.
- فاز ۳: CDC به‌کمک Change Tracking/rowversion در صورت فعال بودن روی SQL Server و reconciliation زمان‌بندی‌شده.

## کنترل کیفیت و rollback

- تست اتصال قبل از فعال‌سازی، محدودیت batch، timeout و ثبت خطای بدون secret.
- هر row دارای `source_key` و `content_hash` است؛ sync قابل تکرار و قابل audit است.
- خاموش‌کردن افزونه اجرای آینده را متوقف می‌کند و داده mirror را حذف نمی‌کند.
- حذف داده فقط با عملیات مدیریتی جداگانه و صریح انجام خواهد شد.

## معیار پذیرش

- رمز عبور در API بازگردانده نشود.
- اتصال read-only و catalog discovery موفق باشد.
- sync دوم روی داده بدون تغییر، duplicate نسازد.
- خطای یک جدول کل run را قابل تشخیص کند.
- صفحه تنظیمات امکان تست اتصال، کشف جدول‌ها، ذخیره تنظیمات، اجرای دستی و مشاهده وضعیت را بدهد.

## جزئیات اجرای نسخه فعلی

- لایو در این نسخه به معنی polling قابل تنظیم (۱ تا ۱۴۴۰ دقیقه) است؛ CDC آنی در فاز ۳ قرار دارد.
- قفل advisory روی اتصال اختصاصی PostgreSQL از اجرای هم‌زمان دستی/خودکار در چند worker جلوگیری می‌کند؛ موعد اجرا پس از گرفتن قفل دوباره بررسی می‌شود.
- تنظیمات و عملیات فقط با دسترسی مدیریت تنظیمات کسب‌وکار قابل استفاده‌اند؛ worker نیز اعتبار افزونه را بررسی می‌کند.
- جدول بدون کلید اصلی با hash محتوا و شماره تکرار ذخیره می‌شود. تغییر چنین رکوردی نسخه جدیدی از داده خام ایجاد می‌کند؛ نسخه فعلی حذف‌های مبدا را به حسابیکس منتقل نمی‌کند.
- داده خام در جداول اختصاصی افزونه نگهداری می‌شود؛ نمایش در اسناد و گزارش‌های بومی حسابیکس به نگاشت فاز ۲ وابسته است.

## فاز ۲ — تبدیل بومی (۲۳ اکتبر ۲۰۲۶)

- هویت پایدار در `sepidar_native_maps` با کلید کسب‌وکار، دیتابیس، جدول و شناسه مبدأ؛ fingerprint هدر و اقلام برای تشخیص تغییر.
- ترتیب: ارز و سال مالی → انبار مرجع → اشخاص/تماس اصلی → کالا/واحد → درخت حساب‌ها → اسناد و سطرهای دفتر → فروش، برگشت فروش، خرید و پیش‌فاکتور.
- کد حساب از مسیر والدها ساخته می‌شود؛ کدهای تکراری در شاخه‌های مختلف سپیدار ادغام نمی‌شوند.
- پیشوند گزارش بومی به مسیر اصلی `SPD` اضافه می‌شود؛ گروه‌های استاندارد سپیدار به دارایی/بدهی/سرمایه/درآمد/هزینه متناظر نگاشت می‌شوند. گروه مختلط بر اساس ماهیت بدهکار/بستانکار تعریف‌شده در مبدأ طبقه‌بندی می‌شود، نه مانده لحظه‌ای. نوع بومی حساب `accounting_document` است.
- در فروش/برگشت یک‌به‌یک، وقتی تاریخ، ارز و سال مالی یکی باشد، همان سند سپیدار به عنوان فاکتور بومی استفاده می‌شود. در سایر موارد فاکتور به سند دفتر لینک می‌شود؛ هیچ ثبت بدهکار/بستانکار جدیدی از روی فاکتور تولید نمی‌شود.
- تراز هر سند، برابری جمع هدر و اقلام، ارزها، سال مالی و تمام ارجاعات پیش از commit کنترل می‌شوند. کل تبدیل بومی در یک تراکنش است؛ شکست، اشخاص/کالاها و اسناد نیمه‌کاره باقی نمی‌گذارد.
- پس از هر snapshot موفق، در صورت فعال بودن `native_enabled`، همین نگاشت روی رکوردهای موجود اعمال می‌شود. داده بدون تغییر دوباره ساخته نمی‌شود.
- داده‌های مالی منبع‌مدیریت‌شده از مسیرهای ویرایش/حذف فاکتور و سند قفل هستند؛ ایجاد داده جدید محلی مستقل است. حذف فیزیکی رکورد مبدأ یا تغییر ارتباط اسناد مالی نیازمند reconciliation است و خودکار باعث حذف دفتر نمی‌شود.
- حذف مبدأ در snapshot با tombstone نگه‌داری می‌شود؛ داده خام از بین نمی‌رود. این نسخه گردش/موجودی انبار و تسویه دریافت/پرداخت را به اسناد انبار/پرداخت بومی تبدیل نمی‌کند؛ شناسه‌ها و داده‌های آن‌ها در snapshot و فراداده حفظ می‌شوند.
- آزمون‌های PostgreSQL: عدم تکرار، جلوگیری از دو بار ثبت دفتر، به‌روزرسانی با حفظ شناسه، rollback خطای مالی، مرجع ناموجود، حفاظت اسناد و مسیر کامل polling → snapshot → native.
- تا ورود بهای تمام‌شده انبار، محاسبه تحلیلی سود فاکتور واردشده غیرفعال است؛ هزینه نامعلوم هرگز به‌عنوان هزینه صفر و حاشیه سود ۱۰۰٪ نمایش داده نمی‌شود. گزارش دفتر بر مبنای اسناد اصلی سپیدار مستقل باقی می‌ماند.
