# افزونه تولید پیشرفته — سند زنده توسعه

> **وضعیت سند:** زنده (Living Document) — پس از هر تصمیم معماری، تکمیل گزارش، یا تغییر هسته به‌روز می‌شود.  
> **تاریخ ایجاد:** ۲۰۲۶-۱۱-۰۴  
> **آخرین به‌روزرسانی:** ۲۰۲۶-۱۱-۰۵  
> **فاز جاری:** کاتالوگ گزارش‌ها در افزونه پیاده شده است. هوک دفتر کل فقط با افزونه فعال و حساب نگاشت‌شده اجرا می‌شود. تصمیم‌های باز D-01، D-03، D-05، D-06 و D-08 در کد حدس زده نشده‌اند.  
> **کد پیشنهادی بازار:** `advanced_production`  
> **نام نمایشی:** افزونه تولید پیشرفته  
> **دسته پیشنهادی بازار:** `operations`

این فایل منبع واحد توسعهٔ افزونه است. هر گزارش و قابلیت باید اول اینجا ثبت شود، بعد پیاده‌سازی شود، بعد وضعیت همین سند به‌روز شود.

## ۲) خلاصه محصول

افزونهٔ **تولید پیشرفته** لایهٔ صنعتی حسابیکس برای کارگاه بزرگ و کارخانه است: برنامه‌ریزی، مصرف مواد، بهای تمام‌شده، WIP، راندمان، کیفیت و نگهداری.

نسخهٔ کارگاهی امروز در **هستهٔ رایگان** می‌ماند. افزونه آن را حذف یا پولی نمی‌کند؛ روی همان اسناد، گزارش‌ها و موجودیت‌های صنعتی می‌سازد.

### ۲.۱ برای چه کسی

| پرسونا | نیاز اصلی از افزونه |
|--------|----------------------|
| مدیر کارخانه | داشبورد، تحقق برنامه، ضایعات، ظرفیت |
| مدیر تولید | سفارش باز، پیشرفت، مواد کسری، توقف خط |
| حسابدار صنعتی | بهای تمام‌شده سفارش/محصول، انحراف، WIP، سند دفتر کل |
| مسئول انبار تولید | مصرف، برگشت، بچ، کالای در جریان |
| کنترل کیفیت | قبولی/رد، عدم انطباق، ردیابی بچ |
| تعمیرات | خرابی، MTBF/MTTR، سرویس پیشگیرانه |

### ۲.۲ مقیاس هدف

یک طراحی باید هر دو را پوشش دهد:

- کارگاه کوچک با یک یا دو محصول، یک BOM، بدون خط و شیفت
- کارخانه با چند خط، BOM چندمرحله‌ای، نیمه‌ساخته، چند مرکز هزینه، بچ و QC

قابلیت‌های کارخانه پشت افزونه و پشت موجودیت‌های اختیاری می‌مانند. کارگاه کوچک نباید مجبور به تعریف ماشین، شیفت یا کارت QC شود.

### ۲.۳ خارج از محدودهٔ آگاهانه (نسخهٔ اول تا فاز ۷)

- APS/زمان‌بندی بهینه‌ساز ظرفیت (فقط گزارش ظرفیت، نه موتور زمان‌بندی)
- MES لحظه‌ای با PLC / OPC-UA
- MRP کامل خرید خودکار
- چندکارخانه‌ای بین چند `business_id` (هر کسب‌وکار یک واحد است)
- جایگزینی فاکتور تولید هسته با سند جدید
- تبدیل اجباری BOMهای موجود

این موارد فقط با ردیف جدید در changelog و تصمیم صریح وارد محدوده می‌شوند.

## ۳) معماری قفل‌شده

### ۳.۱ دو حوزه متصل، نه یک ماژول درهم

```
┌─────────────────────────────────────────────────────────────┐
│                 افزونه تولید پیشرفته                         │
│  لایسنس: advanced_production                                 │
├──────────────────────────────┬──────────────────────────────┤
│  مدیریت عملیات تولید         │  حسابداری صنعتی              │
│  Production Management       │  Cost Accounting             │
│                              │                              │
│  BOM، مراحل، سفارش، خط،      │  مواد مستقیم، دستمزد، سربار  │
│  ماشین، مصرف، ضایعات، QC،    │  جذب سربار، WIP، انحراف،     │
│  پیشرفت، بچ                  │  سند دفتر کل، روش بها        │
└──────────────┬───────────────┴──────────────┬───────────────┘
               │                              │
               ▼                              ▼
     سفارش تولید هسته +               اسناد مالی هسته
     فاکتور تولید / ضایعات            حساب‌ها / انبار / کالا
```

وقتی سفارش تکمیل می‌شود، مصرف مواد، عملیات و ضایعات باید با شناسهٔ قابل ردیابی وارد محاسبهٔ بها شوند. گزارش عملیاتی بدون بها، و بها بدون سند عملیاتی، هر دو ناقص‌اند.

### ۳.۲ هسته رایگان در برابر افزونه

الگوی مشابه: چاپ برچسب ساده در هسته / استودیو برچسب در افزونه؛ اسناد حسابداری در هسته / صورت‌های مالی در بسته حسابداری پیشرفته.

| در هسته می‌ماند (رایگان) | پشت افزونه می‌آید |
|--------------------------|-------------------|
| تعریف BOM (مواد، خروجی، عملیات، نسخه) | داشبورد مدیریت تولید |
| فاکتور تولید از انفجار BOM | گزارش‌های صنعتی فهرست‌شده در بخش ۱۰ |
| فاکتور ضایعات و مصرف مستقیم | روش‌های بها: استاندارد، واقعی، میانگین موزون به‌صورت انتخاب کسب‌وکار |
| سفارش تولید: پیش‌نویس → آزاد → در جریان → تکمیل / لغو | WIP حسابداری و مغایرت فیزیکی |
| رزرو مواد و برنامه نیاز مواد | مراکز/خطوط/ماشین/شیفت/اپراتور به‌صورت موجودیت |
| بهای سفارش: مواد و عملیات استاندارد در برابر واقعی | انحراف نرخ، دستمزد، سربار جذب‌شده |
| ردیابی بچ/لات روی سفارش | QC، OEE، CMMS |
| دو گزارش فعلی: تولید و مصرف مواد | فیلتر خط/شیفت/اپراتور، مقایسه دو دوره، drill-down صنعتی |

### ۳.۳ منبع حقیقت اسناد

تغییر نمی‌کند مگر با تصمیم صریح در همین سند:

1. **انفجار BOM فقط از مسیر فاکتور تولید** انجام می‌شود.
2. **حواله انبار** مقدار واقعی ورود/خروج را حمل می‌کند و به سفارش سنکرون می‌شود.
3. **سفارش تولید** برنامه، رزرو، پیشرفت و اسنپ‌شات بها است؛ جایگزین فاکتور نیست.
4. افزونه گزارش و موجودیت می‌سازد؛ چرخه سند هسته را دور نمی‌زند.

### ۳.۴ اتصال به ماژول‌های موجود

| ماژول | نقش در افزونه |
|-------|----------------|
| کالا و BOM | فرمول استاندارد مصرف و عملیات |
| سفارش تولید | محور ردیابی سفارش، پیشرفت، بها |
| فاکتور تولید / ضایعات | ثبت واقعی مصرف، ساخت، ضایعات |
| انبار و لات | موجودی، رزرو، ردیابی بچ |
| حقوق و دستمزد (`payroll`) | منبع بعدی دستمزد مستقیم؛ فاز ۲ فقط جای نگاشت دارد، وابستگی اجباری نیست |
| دارایی ثابت (`fixed_assets`) | اتصال بعدی ماشین به کارت دارایی؛ فاز ۸ |
| پروژه | فیلتر اختیاری روی سفارش در صورت وجود `project_id` |
| HScript | گزارش سفارشی کارخانه؛ سقف و لایسنس جدا می‌ماند |
| MCP / AI | ابزارهای تولید هسته می‌مانند؛ ابزارهای افزونه پشت گیت لایسنس |

### ۳.۵ تأثیر روی هسته حسابداری 🔒

بازنویسی موتور دفتر کل، تراز، بستن سال، یا ثبت فروش/خرید **لازم نیست و ممنوع است.**

هسته همین حالا فاکتور تولید را سند می‌زند. الگوی فعلی در `invoice_service.py`:

```
خروج مواد:     Dr 10106 WIP          Cr 10102 موجودی
سربار عملیات:  Dr 10106 WIP          Cr 70408 سربار تولید
ورود محصول:    Dr 10102 موجودی       Cr 10106 WIP
ضایعات:        Dr 70407 هزینه ضایعات Cr 10102 موجودی
```

این برای کارگاه (یک فاکتور = مصرف + ساخت در همان سند) کافی و متوازن است. حساب `inventory_finished` در resolver هست ولی در ثبت تولید استفاده نمی‌شود؛ ورود و خروج هر دو روی `10102` می‌روند. حواله `production_in/out` موجودی مقداری را جابه‌جا می‌کند و سند WIP جدا نمی‌سازد. در نتیجه ماندهٔ `10106` بعد از فاکتور کامل معمولاً صفر است و سفارش نیمه‌تمام ماندهٔ دفتر ندارد.

| نیاز افزونه | آیا هسته باید عوض شود؟ | شکل مجاز تغییر |
|-------------|------------------------|----------------|
| گزارش سفارش، پیشرفت، مصرف، انحراف مقدار، داشبورد، QC، OEE، تعمیرات | خیر | فقط سرویس و UI افزونه |
| نمایش بهای سفارش (استاندارد/واقعی موجود) | خیر | API فعلی `get_production_order_costing` |
| تفکیک حساب مواد / نیمه‌ساخته / ساخته‌شده | بله، هوک کوچک | استفاده از `inventory_finished` (و در صورت نیاز حساب نیمه‌ساخته) به‌جای `10102` برای ورود؛ پشت گیت افزونه |
| WIP واقعی سفارش باز (مواد صادرشده بدون محصول کامل) | بله، هوک | یا ثبت WIP روی صدور حواله/فاکتور جزئی، یا سند افزونه `production_wip` مثل حقوق/اموال؛ بدون گیت رفتار فعلی صفر شدن WIP حفظ شود |
| سه روش بها (استاندارد / واقعی / میانگین) در ارزیابی موجودی ساخته‌شده | بله، هوک | `cost_price` لایه ورود تولید از موتور افزونه؛ روش ارزیابی سال مالی هسته دست نخورده می‌ماند مگر برای کالای ساخته‌شده با افزونه فعال |
| جذب سربار و انحراف نرخ/دستمزد/سربار در دفتر | بله، هوک یا سند افزونه | الگوی اموال: سند متوازن جدا (`production_overhead_absorption` / `production_variance`) نه بازنویسی فروش. اگر افزونه فعال باشد `production_operations_total` نباید دوباره روی `70408` بنشیند |
| دستمزد مستقیم از حقوق | خیر در هسته فاکتور | سند افزونه با نگاشت حساب؛ وابستگی اجباری به `payroll` نیست |
| بستن سال و تراز | فقط خواندن | اگر WIP سند شده باشد، مانده `10106` خودش در ترازنامه می‌آید؛ منطق بستن سال عوض نشود |

**قانون هوک:** هر تغییر هسته باید پشت `is_plugin_active(..., "advanced_production")` باشد، کسب‌وکار بدون افزونه همان ثبت امروز را ببیند، و سند جدید حتماً متوازن باشد. منطق داخل `create_invoice` بزرگ‌تر نشود؛ شاخهٔ تولید به سرویس قابل تست استخراج شود اگر هوک دوم به بعد لازم شد.

تصمیم باز مرتبط: D-05، D-08.

## ۴) وضعیت فعلی حسابیکس (مبنای کار — ۲۰۲۶-۱۱-۰۴)

بررسی کد هسته، بدون تغییر. این بخش بعد از هر تغییر تولید در هسته باید بازبینی شود.

### ۴.۱ موجود و قابل اتکا

| قابلیت | مسیر اصلی | نکته برای افزونه |
|--------|-----------|------------------|
| BOM نسخه، پیش‌فرض، بازده، پرت، جایگزین | `product_boms` + `bom_service.py` + تب فرمول کالا | `work_center` فقط رشته است، موجودیت نیست |
| انفجار BOM در فاکتور تولید | `bom_explosion_widget.dart` | ردیف‌ها `movement` و `bom_id` می‌گیرند |
| فاکتور تولید / ضایعات / مصرف مستقیم | `invoice_production`, `invoice_waste`, `invoice_direct_consumption` | مجوز نوع فاکتور در `invoice_types` |
| سفارش تولید | `production_orders` + API `/production/orders` | وضعیت‌ها: `draft`, `released`, `in_progress`, `completed`, `cancelled` |
| مواد/خروجی/عملیات سفارش | جداول `production_order_*` | اسنپ‌شات هنگام آزادسازی |
| رزرو و برنامه مواد | `get_production_material_plan` | برای گزارش کسری و مواد موردنیاز |
| بها سفارش | `get_production_order_costing` | مواد و عملیات استاندارد/واقعی + انحراف مقدار و هزینه |
| لات روی مواد و خروجی | `lot_code`, تاریخ ساخت/انقضا | ردیابی با `GET .../trace?lot_code=` |
| ضایعات روی خروجی سفارش | `scrap_quantity` | علت، بازیافت، اپراتور، خط ندارد |
| گزارش تولید هسته | `/reports/production` | فقط خطوط `movement=in` فاکتور تولید |
| گزارش مصرف مواد هسته | `/reports/materials-consumption` | فقط خطوط `movement=out` فاکتور تولید |
| منوی سفارش تولید | `production-orders` | بدون گیت افزونه |
| ابزارهای MCP تولید | `ai_function_extensions_mcp_production.py` | با `inventory.read/write` |

### ۴.۲ شکاف هسته و پوشش افزونه

هسته این‌ها را ندارد و رایگان می‌ماند. افزونه روی رکورد خودش پوشش داده است:

- مرکز، خط، دستگاه، شیفت، و اپراتور اختیاری روی خروجی خط
- دستمزد ثبت‌شده در تولید، جدا از حقوق
- سه روش بها در گزارش و، وقتی حساب‌ها نگاشت شده باشند، در هوک فاکتور تولید
- سن و شمارش جریان ساخت، توقف سفارش، کنترل کیفیت، توقف خط، OEE، تعمیر، دوباره‌کاری و علت ضایعات
- گزارش دوره‌ای بهای محصول

در دفتر کل هنوز بسته نشده و در کد حدس زده نمی‌شود:

- سند پایان دوره برای جریان ساخت (D-05)
- جذب سربار با سند جدا (D-08)
- نرخ استاندارد خرید جدا از نرخ ردیف سفارش

### ۴.۳ تصمیم محدوده در برابر هسته

گزارش‌های فعلی «تولید» و «مصرف مواد» **آزاد می‌مانند**. نسخهٔ افزونه اگر همان موضوع را عمیق‌تر کند، نام و مسیر جدا می‌گیرد (مثلاً «مصرف در برابر BOM») تا کاربر رایگان مسیر فعلی را از دست ندهد.

## ۵) اصول طراحی گزارش و قابلیت

صرف داشتن گزارش کافی نیست. هر گزارش افزونه باید این‌ها را رعایت کند مگر در کاتالوگ صریحاً استثنا شده باشد.

### ۵.۱ فیلترهای استاندارد

حداقل:

- بازه تاریخ. اگر سال مالی انتخاب شود، بازه با شروع و پایان همان سال مالی این کسب‌وکار جمع می‌شود. بازه بیرون از سال، گزارش را خالی می‌کند.
- محصول، سفارش تولید، و انبار. انبار سفارش، انبار مصرف یا انبار محصول نهایی است. انبار سند، انبار ردیف یا سربرگ فاکتور است.
- ارز فقط روی گزارش‌های سندی. مبلغ همان ارز سند است و بین ارزها تبدیل نمی‌شود. بهای سفارش ارز جدا ندارد.

وقتی موجودیت مربوطه ساخته شد:

- مرکز/خط/دستگاه/اپراتور/شیفت
- بچ / سری ساخت
- واحد اندازه‌گیری جایگزین (از واحد کالای هسته، نه واحد موازی جدید)

### ۵.۲ رفتار اجباری UI گزارش

- ذخیره فیلتر جدول با `ListFilterPageIds` و `persistTableFiltersPageId`
- خروجی Excel و PDF از مسیر مشترک `list_report_export_service`
- مقایسه دو دوره (از فاز ۷؛ گزارش‌های تحلیلی باید جای پارامتر `compare_from/compare_to` داشته باشند)
- مقایسه واقعی با استاندارد وقتی BOM یا نرخ استاندارد وجود دارد
- Drill-down تا سند: فاکتور، حواله، سفارش، یا سند دفتر کل
- گیت افزونه روی کارت گزارش و روی خود صفحه (`AdvancedProductionPluginGate`)

### ۵.۳ قرارداد API گزارش

پاسخ همه گزارش‌های لیستی افزونه:

```json
{
  "items": [],
  "summary": {},
  "pagination": { "total": 0, "page": 1, "per_page": 50 }
}
```

فیلترهای مشترک query/body: `date_from`, `date_to`, `fiscal_year_id`, `currency_id`, `product_id`, `warehouse_id`, `production_order_id`, به‌علاوه فیلترهای موجودیت صنعتی وقتی ساخته شدند.

## ۸) روند افزودن یک گزارش (Playbook)

این چک‌لیست برای هر ردیف کاتالوگ تکرار می‌شود. تیک‌ها در یادداشت همان گزارش در بخش ۱۱ زده می‌شوند، نه اینجا.

### ۸.۱ قبل از کد

1. شناسه پایدار انتخاب شود (`AP-...`).
2. منبع داده مشخص شود: هسته / افزونه / هر دو.
3. اگر `blocked-master` یا `blocked-accounting` است، اول موجودیت یا موتور مربوطه.
4. ستون‌ها، فیلترها، KPI خلاصه، و هدف drill-down نوشته شود.
5. مشخص شود نسخهٔ رایگان جدا می‌ماند یا این گزارش کاملاً افزونه‌ای است.

### ۸.۲ بک‌اند

1. تابع گزارش در `app/services/advanced_production/reports/` نه داخل `invoice_service.py`.
2. ورودی: `db`, `business_id`, فیلترهای استاندارد بخش ۵.۳.
3. خروجی: `items` + `summary` + `pagination`.
4. Endpoint پشت `require_business_access` + `require_advanced_production_plugin_active` + مجوز `view`.
5. ستون‌های Excel/PDF در `report_list_exports` یا ماژول export افزونه.
6. ثبت در `ai_reports_catalog.py` با `ui_key` یکسان با کارت UI.
7. اگر MCP باید ببیند: ابزار جدا با گیت افزونه، مثل حقوق و تعمیرگاه.
8. تست: کسب‌وکار بدون لایسنس → ۴۰۳؛ با لایسنس و داده خالی → `items=[]`؛ با فاکتور/سفارش نمونه → اعداد قابل ادعا.

### ۸.۳ فرانت

1. صفحه با `DataTableWidget`؛ `reportModuleKey` = شناسه گزارش بدون `AP-`.
2. `ListFilterPageIds` جدید.
3. مسیر در `main.dart` داخل `AdvancedProductionPluginGate`.
4. نام مسیر در `business_named_route_locations.dart`.
5. کارت در `reports_page.dart`، بخش `production`، با `marketplacePluginCode`.
6. ترجمه `app_fa.arb` و `app_en.arb`.
7. منوی جانبی فقط برای داشبورد و تنظیمات؛ گزارش‌های عادی از صفحه گزارش‌ها باز شوند.

### ۸.۴ بعد از کد

1. وضعیت کاتالوگ → `done`.
2. مسیر فایل‌ها و نام تست در بخش ۱۱.
3. یک خط در changelog.
4. اگر فیلتر جدیدی به قرارداد استاندارد اضافه شد، بخش ۵ به‌روز شود.

### ۸.۵ روند افزودن قابلیت عملیاتی (غیرگزارش)

برای موجودیت، سند، یا موتور (مثلاً مرکز تولید یا اجرای بها):

1. ردیف در بخش ۶ و فاز مربوطه.
2. مدل + migration.
3. سرویس با قوانین حسابداری/عملیاتی قابل تست.
4. API + مجوز مناسب (`manage` / `operate` / `cost` / `post`).
5. UI پشت گیت.
6. اتصال به سفارش/فاکتور هسته بدون دور زدن سند.
7. گزارش‌های `blocked-*` که باز می‌شوند در کاتالوگ به `plugin-ready` یا `done` تغییر کنند.

این بخش خالی است و به‌ازای هر گزارش در حال کار پر می‌شود. الگو:

```md
### AP-XXX-00 — عنوان

- وضعیت: ...
- Endpoint:
- صفحه UI:
- منبع داده:
- فیلترها:
- Drill-down:
- تست:
- انحراف از playbook:
```

### برش ۲۰۲۶-۱۱-۰۴

پیاده شده و پشت لایسنس `advanced_production`:

- تنظیمات: `costing_method` = `actual` | `standard` | `weighted_average` و `overhead_mode` = `bom_operations`
- نگاشت حساب WIP / ساخته‌شده / ضایعات در API ذخیره می‌شود و هنوز در سند دفتر کل استفاده نمی‌شود
- داشبورد: سفارش باز، عقب‌افتاده، در جریان، تکمیل امروز (مرز روز با منطقه زمانی کسب‌وکار)، مقدار ورود فاکتور تولید به تاریخ سند امروز، تعداد ردیف کسری
- گزارش‌ها: `orders`, `progress`, `overdue`, `schedule`, `plan_achievement`, `open_orders`, `cycle_time`, `order_costing`, `material_requirements`, `material_shortage`, `material_variance`
- تاریخ فیلتر ISO `YYYY-MM-DD` است؛ نمایش در UI با تقویم شمسی یا میلادی کسب‌وکار
- انحراف مثبت یعنی نامساعد نسبت به استاندارد
- میانگین موزون = جمع بهای واقعی سفارش‌های تکمیل‌شده تقسیم بر مقدار تولیدشده؛ اگر مقدار صفر باشد به بهای واقعی همان سفارش برمی‌گردد
- MCP: `get_advanced_production_settings`, `update_advanced_production_settings`, `get_advanced_production_dashboard`, `get_advanced_production_report`
- گزارش AI با پیشوند `advprod_` و همان گیت افزونه

## ۱۳) تست، داده نمونه، پذیرش

### ۱۳.۱ حداقل تست هر فاز کد

- لایسنس خاموش → API 403 با `plugin_code=advanced_production`
- لایسنس روشن + بدون داده → لیست خالی، نه خطا
- سفارش هسته بدون فاکتور → پیشرفت صفر، مواد موردنیاز > ۰
- فاکتور تولید متصل به سفارش → مصرف و ساخت در گزارش و بها منعکس شود
- توازن سند دفتر کل اگر `post` در فاز باشد

### ۱۳.۲ داده نمونه

اسکریپت‌های موقت دمو سیمان در `hesabixAPI/scripts/_tmp_seed_saman_*.py` الگوی کارخانه دارند (BOM چندمرحله، فاکتور تولید، ضایعات). برای افزونه یک seed رسمی و قابل تکرار جدا ساخته می‌شود؛ اسکریپت‌های `_tmp_` وارد محصول نمی‌شوند.

### ۱۳.۳ معیار پذیرش محصول فاز ۲

یک حسابدار صنعتی بتواند برای یک سفارش تکمیل‌شده در گزارش بهای سفارش بگوید:

- مواد استاندارد چقدر باید مصرف می‌شد و چقدر شد
- عملیات/سربار استاندارد و واقعی چقدر است
- بهای واحد محصول از کدام اسناد آمده
- عدد گزارش با جزئیات سفارش یکی است

اگر این چهار مورد برقرار نباشد، فاز ۲ تمام نشده و فازهای وابسته شروع نشوند.
